# Transport contracts

The OpenAPI document exposed by `Fabrik3D.Server` is the REST transport source of truth. Its version is currently `v1`; compatible additions are allowed within this version, while breaking changes require a new versioned route and document.

Generated artifacts live in `Fabrik3D/fabrik3d-ts-contracts`:

- `openapi.json` is the committed Swagger snapshot.
- `src/orchestrator.generated.ts` is generated by `openapi-typescript`; do not edit it manually.
- `src/index.ts` exposes the normalized REST response types and the common API error class.
- `src/signalr.ts` contains the typed SignalR event schemas and hub event names because SignalR is not represented by OpenAPI.

Both Vue clients import `@fabrik3d/contracts` through local Vite and TypeScript aliases. Their API services remain intentionally small: they resolve a backend base URL, perform fetch calls, and translate failed HTTP responses into `OrchestratorApiError`.

## Contract change workflow

1. Change a C# DTO, endpoint, or documented error response in `Fabrik3D.Contracts` or the server.
2. Start the server with the `Testing` or `Development` environment.
3. Run `npm run contracts:generate` from the repository root.
4. Update application adapters only if the generated type exposes a meaningful behavior change.
5. Run the backend and frontend test/build gates.
6. Commit the OpenAPI snapshot and generated TypeScript output with the server change.

CI runs `npm run contracts:check` against the live server. It fails when the server contract, snapshot, or generated TypeScript output has drifted.

## Error payload

All normalized API errors use this JSON shape:

```json
{
  "code": "validation_failed",
  "message": "One or more request fields are invalid.",
  "status": 400,
  "details": { "name": ["The Name field is required."] }
}
```

Existing routes and HTTP status codes remain compatible. Consumers should use `code` for programmatic behavior and `message` for operator feedback.

Orchestration-specific error codes: `invalid_job_transition`, `invalid_task_transition`, `concurrent_modification`, `session_not_owned`, `session_already_claimed`, `job_not_claimable`, `task_not_runnable` — see `ORCHESTRATION.md`.

## Correlation ids

Every request receives an `X-Correlation-Id` header (reused when present, otherwise generated by the server middleware) that is echoed on the response, attached to server logs, and carried in the `JobStateChanged`, `SimulationStateChanged`, and `TaskStateChanged` SignalR events. The clients generate a per-command correlation id for mutating calls.

## SignalR additions

SignalR event payloads are hand-mirrored in `src/signalr.ts` (SignalR is not part of OpenAPI). Keep that file in sync with `Fabrik3D.Contracts/Events/HubEvents.cs`; the contract serialization tests cover both sides.
